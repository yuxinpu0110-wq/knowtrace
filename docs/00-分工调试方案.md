# 知溯KnowTrace —— 分工调试方案

> 目标：把「编辑 → 提问 → 定位 → 诊断 → 选节点 → 学习 → 点亮 → 返回」这条主链路拆成 5 个独立页面（路由），每个人只负责一个环节，各自调试通过后，由整合人（7号）收口合并成新版本。

## 页面与环节对应（路由即环节）

| 路由 | 环节 | 负责人（模块号） | 文档 |
|------|------|------------------|------|
| `/` | 首页 / 知识图谱渲染 + 两按钮 | 1号（图谱渲染） | `01-首页-图谱渲染.md` |
| `/edit` | 编辑：导入教材建图 + 节点状态（删除/已掌握） | 2号（建图） | `02-编辑-建图.md` |
| `/problem` | 提问：识别 + 定位相关节点 | 3号（识别）+ 4号（定位） | `03-提问-识别与定位.md` |
| `/test` | 诊断：选择题多轮追问，出薄弱点提示 | 5号（诊断） | `04-诊断-选择题.md` |
| `/learn` | 学习：单节点教学 + 验证 + 点亮 | 6号（教学） | `05-学习-教学与验证.md` |
| 左下角 ⚙️ | 设置 API Key（跨环节） | 7号（整合） | `06-设置与APIKey.md` |

## 运行环境（每个人都要先跑起来）

- 后端：`cd backend && npm install && npm start`（端口 3001，失败自动回退 Mock，不崩溃）。
- 前端：`cd frontend && npm install && npm run dev`（Vite 开发端口，`/api` 已代理到 3001）。
- 打开浏览器直接访问对应路由调试：`http://localhost:5173/edit`、`/problem`、`/test`、`/learn`、`/`。
- **API Key**：两种方式二选一（见 `06-设置与APIKey.md`）：
  1. 左下角 ⚙️ 输入 key（只存后端内存，推荐给调试用）；
  2. 后端环境变量 `DEEPSEEK_API_KEY`。
- 无 key 时全链路走内置 Mock/规则实现，也能跑通，方便无 key 环境调试 UI。

## 数据/契约（红线，全员遵守）

- 图谱节点 id 必须匹配 `^[a-z0-9_]+$`，关系 `relation ∈ prerequisite|contains|related|contrast`。
- **任何环节不得创造图谱中不存在的 `node_id`**：4号定位、5号诊断、6号教学引用节点时，输出的 node_id 必须来自当前图谱的节点集合。
- **Key / 完整 Prompt / 模型原始推理不得出现在浏览器端**；key 只从后端读取。
- BFS 距离、亮度、颜色、置信度计算一律留在前端 JS，**大模型只产出文本内容**（题干/选项/教学文案/选节点）。
- 契约样例在 `contracts/` 目录，冻结字段不要改，新增字段只能加可选字段。

## 主链路接口一览（后端 `backend/server.js`）

| 接口 | 环节 | 入参 | 出参 |
|------|------|------|------|
| `POST /api/graph/generate` | 建图 | `{ markdown }` | `{ graph: { book_id, nodes[], edges[] } }` |
| `POST /api/question/recognize` | 识别（暂 Mock） | `{ text }` | `{ problem_markdown, subject, confidence, ... }` |
| `POST /api/question/locate` | 定位 | `{ recognized_question }` | `{ seed_nodes: [{node_id, relevance, reason}] }` |
| `POST /api/diagnosis/next` | 诊断 | `{ round, question, answer, signal }` | `{ next_question?, next_options?, suspected_gap?, done? }` |
| `POST /api/teaching/generate` | 教学 | `{ node_id }` | `{ node_id, definition, intuition, relation, example, pitfall, verify_question }` |
| `POST /api/teaching/evaluate` | 验证 | `{ node_id, answer }` | `{ node_id, mastery, score, evidence, suggested_state }` |
| `POST /api/config/key` | 设置 key | `{ api_key }` | `{ source, has_key }` |
| `POST /api/config/status` | key 状态 | `{}` | `{ source, has_key }` |

## 主链路数据流（前端 `frontend/src/flow/useFlow.ts`）

1. `/edit`：`generateGraph()` → 存 `state.graph`。
2. `/problem`：`submitQuestion()` → `recognize` → `locate` → 存 `seedNodes/seedId` → 调 `diagnosisNext(round=0)` → `navigate('/test')`。
3. `/test`：`answerDiagnosis(answer, signal)` 多轮（2~5 道），每轮返回多个 `weak_points` 薄弱点（橙红亮度随置信度）；`done` 后 `diagnosisDone=true`，薄弱点仅提示。
4. `/test` 里用户在左侧图谱**点选任意节点** → `chooseToLearn(nodeId)` → `navigate('/learn')` + `teachingGenerate`。
5. `/learn`：`evaluateAnswer(answer)` → `suggested_state==='green'` 时把该节点加入 `masteredIds`（点亮绿色）→ 返回首页。

## 收口合并（7号）

1. 各环节负责人只改自己环节对应的文件，合并时按文件冲突最小化处理：
   - 2号只动 `backend/adapters/graph.js`（及 `2.module-2-md2graph/`）。
   - 4号只动 `backend/adapters/locate.js`。
   - 5号只动 `backend/adapters/diagnosis.js` + `backend/mocks/diagnosis.js`。
   - 6号只动 `backend/adapters/teaching.js` + `backend/mocks/teaching.js`。
   - 3号只动 `backend/mocks/recognize.js`（接入真实识别时再新增 `backend/adapters/recognize.js`）。
   - 4号只动 `backend/adapters/locate.js` + `backend/mocks/locate.js`。
   - 前端视图每个环节独立一个文件（`views/EditView.tsx` 等），互不冲突。
2. 合并后跑 `cd frontend && npm run build`（tsc + vite）确认无类型错误，再跑后端 `npm start` 全链路手测。
3. 每个环节都配了「验收清单」，合并前各自保证自己的清单全过。

## 通用约定

- 后端统一「真实优先、失败回退 Mock」（`server.js` 的 `serve()`），所以任何环节出错都不会让整条链路崩。
- 前端统一「接口失败自动降级 Mock」（`api/api.ts` 的 `call()`），后端挂了 UI 也能演示。
- 诊断选择题契约：`next_options: { text, signal: 'correct'|'fuzzy'|'dontknow' }[]`，共 3 项，signal 决定置信度更新（correct 降、fuzzy/dontknow 升）。
